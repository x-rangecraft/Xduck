# 同构开发设备发布

`baseline.json` 记录公共发布版本与 STM32 固件校验值；`devices.json` 记录逐台身份和安装状态。
连接使用 `60-tools/ssh-rk3566.sh --device 121|122|124`。原有构建/同步入口仍只指向 121。

首次安装输入保存在 `30-artifacts/rk3566/fleet/<版本>/`，包括签名 `dist/`、从该发布包
提取的 `bootstrap/bin/updaterd`、121 的公共运行依赖归档、签名公钥、公共配置及校验清单。
仅复制运行依赖，不复制签名私钥、121 的模型历史或电机标定。新机使用发布包的开发模型种子。
安装配置与 121 的开发基线一致：信任相同开发签名公钥，禁用定时检查及自动安装。

首次安装脚本明确要求设备编号、SoC 序列号、STM32 by-id 文件名、独立 machine-id 和预期
发布版本五项参数，并拒绝覆盖已有平台配置、模型历史或标定。执行前先确认系统和硬件身份，
审查包内容并在已核实的目标上安装缺失依赖。安装后设置持久名称：122 为 `xduck2`，124 为
`xduck3`。网页从 `configd` 读取设备名称，不按机器分别编译页面。

`check-device.py` 是在目标机执行的 30 秒只读检查：确认实际程序路径、自启动、控制循环、
系统资源、网页响应和未使能状态，并单独记录摄像头与电机是否实际接通。没有硬件反馈不应
误报整机运动验收通过。重启后检查一次；之后只有代码变化或验收失败时才重复相关检查。

后续升级复用 `dist/`，通过各台 `robotctl update apply daemon --from <dist>` 的签名及
健康门禁进行，不再次执行首次初始化脚本。升级前后比对各台独立模型/策略的校验清单。
现有发布包的 postinstall 会启用所带服务；无 ToF 的本批设备升级后须再次执行
`systemctl disable --now tofd.service`，并核实 disabled/inactive。
任何当前使用的模型/策略若不兼容新平台，应在升级前处理，不允许为对齐平台而静默替换。

STM32 使用已核实 UID 的 CMSIS-DAP/SWD 目标；先备份原闪存，再烧录统一正式镜像并 verify。
首次安装和平台升级均不发送电机使能或运动命令。设备安装日志与实机检查证据保存在
`50-logs/deploy/rk3566/fleet/`，其中 Journal 导出只是诊断快照。
