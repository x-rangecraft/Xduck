# 三台同构 Xduck 的统一发布范围

日期：2026-10-19。状态：121、122、124 已统一安装 `0.10.0-dev.local.1792394196.g02f38e4`，两台新设备均完成 STM32 烧录校验、平台安装、重启及 30 秒只读验收。网页在未连接状态已实测分别显示 `xduck2`、`xduck3`。未制作或重刷系统镜像，沿用已核实一致的 K11C Debian 12 / 6.1.141 系统基线。

用户确认三台设备硬件一致：K11C RK3566、STM32H723、相同的 14 电机配置。开发阶段统一系统和平台软件，模型及策略允许逐台独立迭代。

## 统一与独立的边界

| 内容 | 管理规则 |
|---|---|
| 系统镜像、内核、驱动、运行依赖 | 使用同一经过验收的 K11C Debian 12 基线，记录镜像校验值与依赖版本 |
| Xduck 程序、网页、服务、公共硬件配置 | 三台安装同一份签名发布包，使用同一版本及产物校验值 |
| STM32 控制固件 | 三台使用同一正式固件，记录 BIN 校验值、源码来源和 DMUSB 兼容关系 |
| 模型 ONNX、策略 Python、选择及版本历史 | 各台独立，不因平台版本对齐而强制替换；平台 API 兼容性仍须检查 |
| 电机零位、限位、站姿 | 各台独立标定，禁止复制第一台的标定数据 |
| hostname、machine-id、SSH 主机密钥、网络设置、设备名称、STM32 USB 序列号 | 各台独立，使用设备配置登记；不得复制整机身份 |
| 日志与实验结果 | 保留各台原有数据，沿用工程规范中的存储位置 |

这里的“同一整机发布版本”只绑定系统基线、平台发布包和 STM32 固件。模型与策略可以记录当前版本供追溯，但不参与三台版本一致性的判定。平台运行器、隔离机制和安全门禁属于公共平台代码，不属于可逐台分叉的用户策略。

## 已有能力与实施缺口

- 现有应用部署使用签名包、版本目录切换和健康门禁；系统镜像与 STM32 烧录不属于应用 updater 的更新范围。
- `40-deploy/rk3566/remote/deploy-rk3566-microduck.sh` 当前绑定第一台的 hostname、machine-id 和 STM32 稳定串口路径，且每次部署重新构建、生成版本；不能直接用于三台安装同一产物。
- 该脚本会打包默认 ONNX；`robotd/src/models.rs` 会为旧记录迁移默认策略，并自动升级标记为平台默认的消费代码。实现模型/策略独立时必须显式检查这些行为，不能把“保留 /var/lib/robotd/policies”视为策略绝不变化的保证。
- 当前脚本禁用了未配置正式发布源的自动安装；尚未具备三台集中管理面板。统一产物与集中远程操作是两项不同能力。

## 实施顺序与验收条件

1. 登记两台新设备的连接地址、SSH 端口/用户、经核实的主机指纹、hostname、machine-id 和 STM32 USB 稳定路径；保留第一台现有身份校验，不通过跳过校验扩展设备。
2. 确认当前开发代码与实机的验证状态，选定发布候选。构建一次并归档平台签名包、STM32 ELF/BIN/HEX、校验清单、源码修订及工作区差异来源；三台复用这份不可变产物。
3. 分离首次初始化与后续升级：新设备安装统一系统基线、依赖和公钥，私钥只留在受管理的签名端。应用升级与 MCU 烧录分别记录结果，不宣称跨两者具备原子回滚。
4. 平台升级前快照各台模型、策略、清单及选择，检查新平台 API 与现有策略兼容性；默认策略自动迁移若会改动本次应保留的文件，必须先完成部署机制调整，不能直接套用旧流程。
5. 每台分别烧录并回读验证 STM32、安装平台包、完成本机标定与健康验收。只读检查和软件安装不等于运动验收，不自动使能电机。
6. 核对三台系统基线、实际运行程序版本/校验值、STM32 固件校验值及协议能力一致；核对模型和策略内容、活动选择及历史符合逐台保留要求。首次安装没有旧模型时可使用明确记录的开发种子，之后不强制对齐。

所有执行遵循 [ENGINEERING_WORKFLOW.md](ENGINEERING_WORKFLOW.md)。实施入口与清单见 `40-deploy/rk3566/fleet/`；逐台验收证据见 `50-logs/deploy/rk3566/fleet/`。用户已确认 122 只需完成固件部署，电机电源和摄像头尚未连接；未进行电机标定、使能或运动验收。124 的 hostname、SoC 序列号及 STM32 UID 已分别核实；本次同样只完成固件部署，未进行电机标定、使能或运动验收。
