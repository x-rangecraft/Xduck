# Xduck1 两文件策略导入、执行与回滚方案

日期：2026-09-10  
状态：需求整理与实施设计草案，尚未实现  
适用项目：`DuckResource/Xduck/`  
目标设备：Xduck1 / RK3566；电机最终通过现有 STM32 链路控制

> 本文汇总用户已经明确的要求，并给出可供研发评审和后续实施的方案。标为“建议”“第一版范围”“待实测”的内容是设计提案，不代表现有系统能力或已经确认的性能指标。本文不授权部署、启动策略或电机测试，也不替代现行工程与硬件协议规范。

## 1. 背景与目标

现有模型导入围绕固定策略定义实现。研发能够替换模型，以及绑定部分控制参数，但难以独立改变观测构成、观测维度、动作解释、历史窗口、滤波和控制量计算。

用户希望平台提供实际可获得的原始数据，由研发按需要选择和组合这些数据；经过 ONNX 推理后，由研发自己的后处理生成平台需要的 MIT 电机控制目标。平台承担编译或运行环境、硬件通信和硬件保护，使研发可以只替换策略文件开展实验。

目标从“替换一个 ONNX 模型”升级为“替换一套完整的控制策略”。

用户已确认由最初三个文件调整为两个文件：前后处理合并为 `policy.py`，ONNX 独立保留。交付数量减少，前处理→推理→后处理三个执行阶段及平台保护边界不变。

成功标准：研发修改 obs、模型结构或动作解释时，只要满足公开接口和平台资源条件，就可以上传两个文件完成验证和切换，无需修改 robotd、重新编译平台程序或调整底层电机协议。

## 2. 已明确的用户要求

1. 上传入口恰好包含两个文件：`policy.py` 和 `model.onnx`；前处理与后处理合并在同一个策略代码文件中。
2. 平台提供可获得的原始数据，研发自行选择和组装。
3. obs 的维度和内容由研发定义。
4. ONNX 推理后的裁剪、计算、动作转换由研发定义。
5. Kp、Kd、动作缩放、算法层步长限制、滤波等由研发定义。
6. 最终生成平台接受的 MIT 控制下发格式，由平台下发电机。
7. 硬件保护始终由平台兜底。
8. 保留导入与回滚能力，并适配不同 obs 维度和不同模型输出。
9. 需要明确预加载、预处理、预热和正式启用之间的关系。

“平台提供运行环境”不意味着放弃数据契约、状态管理、时限管理和硬件保护。上述能力是不同研发策略可以可靠接入同一台设备的基础。

## 4. 总体架构与职责

```text
电机 / IMU / 操控输入
           │
           ▼
robotd 提供带时间与有效性信息的数据快照
           │
           ▼
独立策略工作进程
  policy.preprocess() → model.onnx → policy.postprocess()
           │
           ▼
统一的逐关节 MIT 控制目标
           │
           ▼
robotd 校验、控制权管理、硬件保护、协议适配
           │
           ▼
STM32 → 电机
```

### 4.1 平台负责

- 硬件数据采集、时间标记和有效性标记。
- 提供清楚的单位、坐标系、关节映射和标定信息。
- 提供版本明确的策略运行环境和 SDK。
- 两文件上传、完整性校验、候选准备、版本存储和回滚。
- ONNX Session 创建、张量校验、完整链路试跑和预热。
- 策略工作进程的生命周期、资源限制和超时检测。
- 唯一控制权、命令新鲜度校验、硬件保护、协议编码与电机下发。
- 记录执行状态、错误和平台对目标的处理结果。

### 4.2 研发负责

- 选择输入数据，定义 obs 顺序、形状、归一化和坐标变换。
- 定义历史窗口、循环模型隐状态和初始化逻辑。
- 导出与前后处理一致的 ONNX。
- 解释模型输出，计算关节目标、Kp、Kd、前馈力矩。
- 定义算法滤波、单步变化限制、动作缩放和推理节奏。
- 提供清楚的接口声明，使平台可以验证兼容性。
- 验证处理逻辑与训练定义的一致性，以及策略的实际运动效果。

### 4.3 保持现有服务边界

robotd 仍是唯一能驱动电机并作安全裁决的服务。策略进程仅计算目标，没有电机总线访问权，也不持有系统使能权限。mediad 负责上传和状态展示，不成为策略或电机状态所有者。

## 5. 两文件交付形式

第一版建议文件角色如下，用户文件名可不同，上传时显式指定角色：

```text
policy.py
model.onnx
```

### 5.1 为什么建议 Python

Python 与 NumPy 便于研发复用训练与仿真中的处理代码，适合频繁调整 obs、滤波和动作映射。ONNX Runtime 执行网络推理。

该选择是实施建议，最终需用 RK3566 的端到端测试确认性能。Python 不提供硬实时保证。未来可考虑其他处理后端，但不将多语言执行器列为第一版前置条件。

### 5.2 两文件约束

- ONNX 必须自包含，不引用另一个外部权重文件。
- 策略文件使用平台提供的依赖，不在导入时联网安装依赖。
- 归一化均值、方差、动作比例等策略常量放在处理文件中，或在适合时并入 ONNX。
- 第一版不依赖随意读取本机路径、额外配置或训练目录。
- 如未来确实需要大型外部资源，应明确扩展交付协议，不能通过隐藏依赖破坏两文件可回滚性。

### 5.3 不需要第三个用户配置文件

接口版本、数据需求、输入输出规格、周期和控制关节等声明放在 `Policy.describe()` 中。平台自动生成内部版本清单。

内部清单不是第三个上传文件。它记录平台识别出的契约、两文件校验值、运行环境版本、校验结果、创建时间和版本 ID。

### 5.4 合并文件后的职责与收益

`policy.py` 同时承载接口声明、统一初始化、前处理和后处理。关节顺序、默认姿态、归一化常量和动作参数可以在同一处定义；前后处理通过同一个实例共享历史与滤波状态，避免两份配置不一致。

文件合并不把推理调用交给研发脚本。平台仍加载和拥有 ONNX Session，依次调用 `preprocess()`、执行推理、调用 `postprocess()`，分别统计耗时和定位错误。`policy.py` 不自行创建第二个推理 Session，也不直接访问电机。

修改前处理或后处理都意味着 `policy.py` 发生变化，需要与选定 ONNX 重新组成完整候选版本并验证。不会出现单独更新前处理后绕过完整链路检查的入口。

## 6. 平台输入数据契约

### 6.1 数据快照建议结构

| 数据组 | 建议内容 | 说明 |
|---|---|---|
| 帧信息 | 序号、单调时钟时间、实际 dt | 用于时序和结果过期检查 |
| 电机反馈 | 位置、速度、可用力矩反馈、在线与故障状态 | 按稳定关节名称访问 |
| IMU 测量 | 加速度、角速度 | 标注轴向、单位与采样时间 |
| 派生姿态 | 可用四元数、投影重力等 | 标注算法来源和有效性，不称为原始测量 |
| 操控指令 | 速度、转向、姿态或模式意图 | 保留物理语义 |
| 机器人信息 | 关节名称、默认姿态、标定版本、映射 | 静态信息可在 reset 时传入 |
| 数据质量 | 有效性、年龄、数据源序号 | 缺失不得伪装成正常零值 |

数据字段清单应以设备链路实际能够提供的内容为准，不承诺当前协议没有提供的测量量。

### 6.2 原始、标定、派生数据要分清

建议区分传感器原始物理测量、经标定映射的关节量、经过融合或滤波的派生量。明确是否已去偏置、是否已转换轴向、是否使用默认姿态作为零点。

平台不应在研发不知情的情况下给输入叠加算法滤波。硬件或固件已经处理的数据应如实标注，不能声称是未处理值。

### 6.3 时间与同步

一次 frame 是一致读取的数据快照，但不保证各硬件同一时刻采样。保留各数据源的采样时间、接收时间或可获得的时间信息，并说明时间域。

无法获得硬件精确采样时间时，明确提供的是主机接收时间。策略可按需对齐或插值，但不能通过插值掩盖平台规定的反馈过期状态。

### 6.4 缺失数据

前处理声明必需和可选数据源。必需数据缺失或过期时，策略返回未就绪或平台拒绝启动；可选数据允许研发显式定义替代方案。

不得因为缺少 IMU 或电机反馈就静默填零，并宣称策略已通过正常输入检查。

## 7. Policy 类与前处理接口设计

以下是拟议接口，前后处理合并在一个 Policy 类中，示例使用 SDK 抽象类型；后续需要落实为真实 SDK 和版本化文档。

```python
class Policy:
    def describe(self):
        return {
            "api_version": 1,
            "period_us": 20_000,  # 示例，不是固定运行周期
            "required_sources": ["joints", "imu.gyro"],
            "inputs": {
                "obs": {"dtype": "float32", "shape": [1, 96]},
            },
            "outputs": {
                "actions": {"dtype": "float32", "shape": [1, 28]},
            },
            "controlled_joints": ["left_hip", "right_hip"],
        }

    def reset(self, robot_info, first_frame):
        # 设置 self.history、self.hidden、self.filter_state 等实例状态。
        # 前后处理共用此初始化入口，不返回另一个独立状态对象。
        ...

    def preprocess(self, frame, feedback):
        # ready=False 时说明等待原因，此轮不执行模型。
        return PreprocessResult(ready=True, inputs={"obs": obs_tensor})

    def postprocess(self, outputs, frame):
        # 与 preprocess 使用同一实例；完整说明见第 9 节。
        return PostprocessResult(targets=motor_targets)
```

`inputs` 按 ONNX 输入名称绑定，不要求名称固定为 obs；obs 只是常见示例。返回张量保留 dtype、rank 和 shape，平台不自动拍平、补零、裁剪或变更类型。

### 7.1 feedback 的语义

feedback 建议包含上一个完成步骤的：

- 模型原始具名输出，供隐状态回传等用途。
- 后处理请求的电机目标。
- 平台已接受或修正的目标及处理原因。
- 若链路支持，发送状态；电机真实响应仍从反馈读取。
- 关联帧序号、有效性和当前运行代次。

“模型原始动作”“后处理目标”“平台接受目标”“电机实际反馈”是不同概念。平台不替研发决定训练中的 previous action 指哪一种。

首次调用 feedback 为空，由 reset 明确初始化。不得使用其他策略留下的反馈。

### 7.2 历史窗口初始化

由研发显式选择重复首帧、预设值填充，或等待真实样本填满。等待期间返回未就绪及原因，平台不下发该策略目标。

设置初始化等待期限，避免错误代码永久停留在等待状态。期限是运行契约的一部分，需要平台接受。

### 7.3 统一实例的生命周期

建议构造函数无必填参数，且只做轻量对象构造。`describe()` 在 reset 之前可调用，返回稳定的接口声明，不依赖历史帧或一次性执行副作用。所有需要真实机器人数据的初始化在 `reset(robot_info, first_frame)` 中完成。

```text
候选准备：加载 policy.py → 创建 Policy → describe → 加载 ONNX
试跑预热：reset → 多轮 preprocess / 平台推理 / postprocess
正式激活：丢弃预热 Policy → 创建新 Policy → 核对声明 → reset
正式运行：preprocess → 平台推理 → postprocess，串行重复
回滚版本：加载对应两个文件，重新执行准备与初始化流程
```

新建实例的声明必须与已经验证的候选契约相同，否则拒绝激活。实例状态不得影响输入维度声明，使同一个文件在准备和正式运行时变成两种接口。

首次 preprocess 的 feedback 为空；同一步前处理与后处理接收同一个数据快照。后处理可以读取该步前处理保存在实例中的中间量，但应明确其生命周期，不依赖偶然的调用顺序之外的异步修改。

重复 reset 必须完全重新初始化可变状态。禁止通过模块全局、可变类属性或可变默认参数保留跨实例历史。平台不能仅靠创建新实例隔离违反该约定的任意 Python 代码；实现时仍需候选进程隔离、测试和运行故障处理。

## 8. ONNX 输入维度与类型适配

### 8.1 核心原则

平台不再拥有一个全局 OBS_LEN。每个候选策略都有自己的输入规格和预分配资源。

| 示例 | 输入规格 | 支持方式 |
|---|---|---|
| 原策略 | `obs: [1,61]` | 按原规格加载 |
| 扩展观测 | `obs: [1,96]` | 为该实例准备 96 维输入 |
| 历史序列 | `obs: [1,10,48]` | 保留三维结构 |
| 循环模型 | `obs`、`hidden` 等 | 每个名字分别校验与绑定 |

### 8.2 三层校验

1. ONNX 元数据：读取所有输入名称、dtype、rank、静态维度和符号维度。
2. 前处理声明：与 ONNX 逐项比较，解析动态维度的具体值。
3. 前处理实际输出：执行后再次验证，防止声明正确而代码返回错误。

对于符号维度，需要检查同一个符号在不同输入中的一致约束。一个模型中共享的 batch 或序列长度不能各自任意取值。

### 8.3 动态形状

若 ONNX 声明 `[batch, obs_dim]`，仅凭文件不能知道实际应输入多少维。前处理需要声明本实例的具体形状，例如 `[1,96]`，平台再试推理。

第一版建议：允许不同策略使用不同尺寸，也允许导出的模型包含动态维度；但每个策略实例在准备时解析出固定运行形状，激活后保持不变。

如确需运行时可变长度，建议研发先使用固定窗口、padding 和显式 mask。对每帧可变形状的直接支持放到后续版本，需要有界内存、输出容量和延迟设计。

### 8.4 dtype 与张量范围

支持的 dtype 应由 SDK、IPC 和实际推理执行器共同明确，不能声称支持 ONNX 的所有类型。第一版优先 float32；常见整数 mask 或索引类型按实际实现加入测试后开放。

第一版使用张量输入输出，不默认支持 sequence、map 或其他 ONNX 复杂值。遇到未支持类型应在导入阶段明确拒绝。

### 8.5 错误示例

```text
PREPROCESS_SHAPE_MISMATCH
输入名称：obs
要求：float32 [1,96]
实际：float64 [1,95]
阶段：完整链路校验，第 3 帧
当前运行版本：未改变
```

形状正确不代表语义正确。例如 gyro 与 gravity 顺序颠倒可能仍满足形状，必须依靠研发对照数据和回放验证。

## 9. 后处理与统一 MIT 出口

### 9.1 不限制模型动作维度等于电机数量

| 输出示例 | 可能含义，仅作说明 |
|---|---|
| `[1,14]` | 14 个关节位置偏移 |
| `[1,28]` | 位置与速度两组参数 |
| `[1,42]` | 位置、Kp、Kd 三组参数 |
| 多个张量 | 动作、估计量、下一步模型隐状态 |

含义必须由后处理代码定义，不能按输出长度猜测。后处理可以只使用模型输出中的动作部分；其余输出可用于前处理下一轮状态。

### 9.2 后处理接口

```python
# 以下方法位于同一个 policy.py 的 Policy 类中。
# describe() 一次声明 inputs、outputs 和 controlled_joints。
# reset() 一次初始化前后处理状态，不重复定义。
def postprocess(self, outputs, frame):
    # 解释输出，更新 self 中的滤波等状态，返回完整电机目标。
    return PostprocessResult(targets=motor_targets)
```

例子只展示接口结构，不是可直接运行的完整策略，也不代表本机真实关节清单。完整模型输出契约需要覆盖实际输出；后处理应显式声明使用哪些输出。

### 9.3 标准电机目标

```python
motor_targets = {
    "left_hip": {
        "position": q_des,
        "velocity": dq_des,
        "kp": kp,
        "kd": kd,
        "torque_ff": tau_ff,
    },
    # 必须完整覆盖声明控制的关节。
}
```

建议使用关节侧统一物理单位：位置 rad、速度 rad/s、力矩 N·m；Kp/Kd 单位与该关节侧控制定义一致。关节侧到电机侧的符号、减速比、零位和增益变换必须由平台执行器适配层明确处理并与现有协议核对，不能假设所有电机可直接透传。

研发可每关节、每帧输出不同 Kp/Kd。算法层的偏移、缩放、滤波、裁剪和步长限制在后处理中完成。平台不应在其后再隐式叠加旧策略的同类处理。

### 9.4 完整性与控制权

- 激活时确定该策略拥有的关节集合。
- 每个控制结果必须覆盖该集合，无重复或未知关节。
- 未接管的关节由平台的明确控制模式管理。
- 不允许多个来源同时写同一个关节目标。
- 不将遗漏字段解释为沿用历史值。
- 非策略流程，例如初始化、放松或故障处理，仍由平台拥有控制权。

### 9.5 请求、接受与实际执行

后处理结果只是请求。平台校验后产生接受目标，再通过实际通信链路发送。反馈中应分别保留这些阶段；若设备不提供逐帧执行确认，不得把“已接受”描述为“电机已经执行”。

平台若执行必要的硬边界处理，需要返回可见原因。正常算法行为不应长期依赖底层裁剪才能工作。

## 10. 状态与循环模型

策略状态包括历史 obs、滤波缓存、上一轮动作、相位计数器、RNN/LSTM 隐状态等。每个运行实例独立持有状态，不跨策略共享。所有可变状态放在 Policy 实例中，禁止使用可变模块全局或类变量保存历史；模块级只保留不可变常量。前后处理串行调用同一个实例，可共享配置与缓存，但不能依赖另一实例或旧版本的状态。

循环模型建议按以下顺序执行：

1. reset 创建初始 hidden 等状态。
2. 前处理生成 obs 与本轮 hidden 输入。
3. ONNX 生成 actions 与 next_hidden。
4. 后处理生成电机目标。
5. 下一轮 feedback 提供上轮具名输出，前处理显式采用 next_hidden。

每次只允许一个逻辑步骤在该实例中推进，避免并发改写状态。若某步骤异常或过期，第一版建议将该运行实例标记失败并进入平台安全流程，不尝试继续使用推进到一半的状态。

预热、激活、回滚、机器人模式切换和故障重启都必须有明确 reset 边界。默认不对任意 Python 状态做通用序列化或跨版本迁移。

## 11. 上传、预加载、试跑、预热和激活

### 11.1 名词定义

| 名词 | 本文含义 |
|---|---|
| 上传 | 接收两个文件并校验完整性 |
| 预加载 | 创建候选进程、加载模块和 ONNX、准备资源 |
| 前处理 | 每轮从平台 frame 构造模型输入 |
| 试跑 | 不下发电机地运行完整计算链路并检查结果 |
| 预热 | 重复执行以完成初始化并观察耗时与资源使用 |
| 激活 | 将通过验证的完整候选版本选为当前版本 |
| 就绪 | 基于正式新鲜数据完成状态初始化和必要历史积累 |
| 使能运行 | 经现有控制流程授权后允许策略目标参与电机控制 |

模型已加载、策略已激活和电机已使能是三个不同状态。前处理、ONNX 推理、后处理仍是三个执行阶段；文件合并不合并这些阶段。

### 11.2 推荐状态机

```text
UPLOADING
  → VALIDATING_FILES
  → PREPARING
  → VALIDATING_PIPELINE
  → WARMING_UP
  → PREPARED
  → ACTIVATING（需重新检查失能与模式条件）
  → INITIALIZING
  → READY_DISABLED
  → RUNNING（单独的初始化/使能流程）

准备失败 → REJECTED，当前版本不变
运行故障 → FAULTED，平台进入既定安全流程
```

状态名是拟议实现名称。版本存储状态与实时运行状态应分开记录，避免把“文件验证通过”当作“正在控制电机”。

### 11.3 上传与完整性

两个文件归属同一个上传事务和候选 ID。未收齐、大小不符或校验失败时不得形成可激活版本。服务端生成路径，不使用用户文件名构造任意磁盘路径。

根据文件角色分别限制大小，同时设总包大小限制。具体上限需评估模型和板端存储后确定，不直接继承旧单文件 64 MiB 为所有新角色的最终规则。

### 11.4 静态与接口检查

检查两个角色的完整性、ONNX 自包含性、运行环境兼容性、Python 语法、Policy 类接口和声明内容。Python 模块导入本身会执行代码，因此 describe 和模块导入也必须在受限候选进程中执行，不能放在 robotd 主进程中。

### 11.5 候选预加载

创建独立实例，加载 ONNX Session、读取图接口、解析动态维度、准备有界通信缓冲和状态资源。无需电机使能，也不会将输出发送给总线。

第一版建议沿用失能条件，在失能时准备候选，减少在运动期间竞争 CPU 和内存的风险。未来如果实测资源充足，可开放低优先级后台准备；该能力不是第一版承诺。

### 11.6 完整链路试跑

运行测试 frame→前处理→ONNX→后处理→目标校验。测试数据优先来自具有明确语义的合成帧、录制片段和只读实时反馈。

不能只使用全零 obs：零姿态未必有效，也不能覆盖前后处理的历史和滤波逻辑。需要连续多帧测试，检查异常、有限值、契约、关节完整性和资源增长。

录制数据应携带数据契约与机器人标定信息；不将其他配置下的数据无条件作为当前设备的可信输入。

### 11.7 预热与性能检查

测量前处理、ONNX、后处理、通信及端到端耗时，记录分位数、最大观测值、超时次数、RSS 和趋势。预热轮数、持续时间、内存上限、时限余量均需板端实测确定。

如策略声明 20 ms 周期，应验证完整链路能在平台预算内完成，不能只比较平均 ONNX 耗时。一次预热通过不是最坏情况耗时证明，正式运行继续执行超时保护。

### 11.8 预热状态不得带入正式控制

预热使用独立试验状态。激活时重新 reset 策略实例与隐状态，同时保留已加载的模型执行资源。建议销毁预热实例，新建 Policy 并 reset，防止遗漏状态。

reset 不得重新导入依赖或重建模型。它的耗时和资源行为也需要测试。若初始化需要积累真实样本，在 INITIALIZING 状态完成，并设置合理期限。

### 11.9 激活时重新检查

必须重新确认目标模式、策略槽位、候选版本、运行环境和机器人配置匹配，并满足现有新鲜 STM32 反馈、所有配置电机实际失能等门禁。

准备期间条件变化不能自动延后到某次失能时悄悄生效。请求应明确失败或返回需要重新发起激活的状态。

## 12. 周期、步长与时序

### 12.1 三种频率要区分

- 传感器数据到达频率。
- 策略前处理、推理、后处理的更新频率。
- 底层硬件通信与目标发送频率。

研发声明策略周期，平台验证硬件能力、数据条件和运算预算。高于传感器更新率时可能重复使用同一采样，必须通过序号和数据年龄让研发可见。

### 12.2 “步长限制”的两种含义

动作每步允许变化多少属于算法，由后处理定义。每轮推理间隔多久属于调度契约，由研发申请、平台校验后执行。

### 12.3 目标保持与插值

第一版建议在有效期内保持最近一个已接受目标；到期按平台既定安全流程处理，不能无限保持。若研发需要轨迹插值，应通过明确支持的接口实现，不隐式加入插值或滤波。

目标有效期由平台根据接受的契约决定，策略不能随意延长以绕过超时。

### 12.4 结果关联与过期丢弃

每个结果携带版本 ID、运行代次、输入 frame 序号和截止信息。平台拒绝旧版本、旧代次、乱序或过期结果。使用有界最新帧交换机制，避免等待队列积累旧输入。

## 13. 工作进程与运行环境

### 13.1 建议进程安排

前处理、ONNX 推理和后处理放在同一个策略工作进程，减少张量跨进程传输。robotd 通过有界本地通道发送数据和接收最终目标。

第一版可以先验证有界 IPC 的端到端性能；是否使用共享内存由实测决定，不预先假设通信成本可以忽略。

### 13.2 隔离要求

工作进程崩溃、死循环或异常不得阻塞 robotd 的硬件通信。进程分离本身不构成完整权限隔离，需要结合受限文件系统视图、设备权限、网络限制和资源限制实现。

进程仅访问自己的只读策略文件、必要运行库和受控 IPC；不授予总线、任意系统写入或外部网络能力。采用目标系统实际可用的隔离机制，具体机制实现前验证。

### 13.3 固定环境

环境版本记录 Python、NumPy、ONNX Runtime、SDK/ABI 和平台构建标识。导入时发现依赖缺失，应明确拒绝；不自动安装未知包。

旧版模型转换虚拟环境是转换用途，不直接假定可承担新策略长期运行。新增运行依赖的位置、安装和升级方式应在实施时更新工程规范。

### 13.4 同时驻留资源

当前实例与候选实例可能同时占用内存。准备前检查资源预算，并限制候选并发数。第一版建议最多一个候选任务；资源不足时排队或拒绝，不影响现有控制进程。

## 14. 硬件保护与算法自由的边界

| 事项 | 所有者 |
|---|---|
| obs 选择、归一化、历史窗口 | 研发 |
| 模型输出含义与动作缩放 | 研发 |
| 算法滤波、单步变化限制 | 研发 |
| 逐关节 Kp/Kd 与前馈计算 | 研发 |
| 合法协议范围、机械硬限位 | 平台 |
| 电机故障、反馈超时、失能和急停 | 平台 |
| 策略运行超时和非法目标处理 | 平台 |
| 初始化、使能授权、唯一控制权 | 平台 |

NaN/Inf、未知关节、重复目标、漏项和过期结果应明确拒绝。超过硬边界时如何拒绝、限幅或进入安全状态，按现有安全机制和具体执行器规范确定，不在本文发明统一的电机保护数值。

保留 STM32 独立保护。现行工程规范中的主机命令超时保护不会因为策略进程仍在运行而失效。

## 15. 版本存储、原子切换与回滚

### 15.1 版本是不可拆分的整体

版本绑定两文件字节内容、契约、运行环境要求和校验值。页面不能只回滚 ONNX 或只替换后处理；任何单文件修改都会产生一个新完整版本。

建议在现有 `/var/lib/robotd/policies/` 受管理区域中扩展目录，具体迁移由实现设计确定：

```text
policies/
  <slot>/
    versions/<version-id>/
      policy.py
      model.onnx
      manifest.json       # 平台生成
    active.json           # 平台生成的当前版本引用
```

用户只上传两个文件；内部元数据由 robotd 唯一写入。发布包中的原始策略不被覆盖。

### 15.2 提交过程

1. 写入暂存目录并校验两文件哈希。
2. 完成候选检查和预热，生成验证记录。
3. 落盘不可变版本内容，确保必要持久化完成。
4. 由控制状态所有者重新检查激活条件。
5. 在无控制目标输出的切换阶段提交持久活动引用并切换实例。
6. reset 正式状态，进入初始化与待使能状态。

磁盘引用和内存实例不是天然的同一个原子操作。实现需要明确提交点、切换中禁止输出、崩溃恢复规则和失败补偿，不能只用 rename 就声称两者同时原子完成。

### 15.3 失败与重启语义

提交点之前失败，旧版本保持有效。持久引用提交后进程崩溃，重启应按已提交完整版本重新校验加载，并保持失能；加载失败时明确报错，不静默启动任意历史策略。

若提交后初始化失败，应进入失败且失能状态，保留旧版本供明确回滚；不得把候选失败状态显示成可运行。

### 15.4 回滚流程

回滚目标先重新验证文件完整性、当前环境和机器人配置兼容性，再走同样的准备、门禁、切换和 reset 流程。

回滚恢复代码和模型版本，不恢复旧的运行时历史、滤波缓存或隐状态。旧包要求的环境版本不存在时应拒绝并说明原因，不能声称记录版本号就实现了环境回滚。

第一版建议保留当前版加最近两个历史版，延续现有用户习惯；应提供两文件下载以便归档。扩展历史数量需评估存储和清理策略。

### 15.5 运行故障不自动恢复运动

策略故障先触发平台安全流程。即使准备好了旧版本，也不在运动中直接切换并继续执行；回滚和重新使能仍需要经过明确控制流程。

## 16. 上传页面与研发体验

页面建议提供两个文件选择框（策略代码、ONNX 模型）、策略名称或备注、目标槽位，以及“上传并验证”“激活”“回滚”“下载版本”操作。

验证后展示：

- 两文件名称、哈希和完整版本 ID。
- 接口与环境版本。
- 模型输入输出的名称、类型、形状。
- 控制关节列表和数据依赖。
- 策略周期、初始化方式与就绪状态。
- 完整链路耗时、内存和验证时间。
- 激活门禁是否满足及具体原因。

Kp/Kd 和动作缩放不再作为页面强制全局覆盖参数，以免与后处理计算发生双重作用。页面可以展示处理文件声明的说明或实际请求值，但不能声称自动理解任意代码的算法含义。

验证通过后保持待激活状态；激活也不自动使能电机。错误必须指出文件角色、阶段、输入名称或关节名称，以及当前版本是否发生改变。

## 17. 日志、回放与可复现性

服务状态与错误写入既有 Journal。离线回放与验收数据按工程规范放入 `50-logs/test/`，不另建长期服务影子日志。

版本清单可以保存紧凑的结构化验证摘要，它是版本元数据，不作为第二份持续运行日志。

记录建议包括版本 ID、环境版本、数据契约、标定版本、阶段耗时、帧序号、故障原因和平台目标处理结果。高频张量采集应显式开启、限量，并通过适合的实验数据通道输出，避免挤占控制资源。

提供电脑端 SDK 和回放工具，使用与板端相同的两文件接口。允许研发先验证前处理、ONNX 和后处理的一致性，但电脑通过不能替代板端环境和性能验证。

若研发有训练端参考输入输出，可用其建立数值对照。平台不能仅凭张量合法证明关节顺序、动作语义或实机稳定性正确。

## 19. 分阶段实施计划

### 阶段 A：冻结接口与示例

产出数据字段字典、单一 Policy 类的 SDK 接口、MIT 目标定义、错误码、状态机和旧策略两文件示例。确认单位、坐标系、状态反馈和就绪语义。

验收：研发能够在电脑上通过同一接口运行示例，并获取清楚的模型输入和控制目标。

### 阶段 B：无电机运行器

实现独立进程、模型加载、具名张量校验、状态 reset、试跑、预热和资源统计。用录制数据与合成策略验证，不接电机出口。

验收：61 维、96 维、历史序列、多输入输出均能分别加载；错误形状、异常、死循环、超时被准确发现。

### 阶段 C：两文件版本管理

实现上传事务、不可变版本、验证任务、激活门禁、持久引用、回滚和页面。

验收：上传中断、单文件损坏、准备失败和提交故障都不会形成混合版本；重启与回滚行为符合定义。

### 阶段 D：robotd 控制接入

实现实时数据快照、有界 IPC、目标适配、控制权与超时处理。先采用不下发的影子计算或 FakeIo 验证，再按已授权流程开展硬件测试。

验收：过期目标、旧版本结果、漏关节和工作进程故障不能进入电机出口；原平台保护持续有效。

### 阶段 E：旧行为一致性与研发试用

使用相同输入序列对比旧实现与默认两文件策略，再测试槽位切换、初始化和滤波状态。由研发提交至少一种不同 obs 和一种不同输出结构的策略验证独立扩展能力。

验收：默认策略无重复缩放/滤波；新增策略无需修改平台源码；板端性能满足已接受周期。

## 20. 测试与验收矩阵

| 类别 | 用例 | 预期 |
|---|---|---|
| 上传 | 只上传一个文件 | 不形成可激活版本 |
| 上传 | 文件角色错误、哈希不符 | 明确拒绝，当前版本不变 |
| 输入 | `[1,61]` 与 `[1,96]` 两套策略 | 分别成功，不依赖全局维度 |
| 输入 | `[1,10,48]` | 保留形状，不拍平 |
| 输入 | ONNX 动态维度 | 由声明解析具体尺寸并试跑 |
| 输入 | dtype、rank、名称错误 | 指明差异，拒绝 |
| 输入 | 激活后返回新尺寸 | 运行故障，不临时猜测适配 |
| 输出 | 14/28 维或多输出 | 经对应后处理产生统一目标 |
| 输出 | NaN/Inf、缺关节、重复关节 | 拒绝目标 |
| 状态 | 历史窗口尚未填满 | 未就绪，不下发策略目标 |
| 状态 | 隐状态初始值与跨帧更新 | 可复现、无跨实例污染 |
| 状态 | 预热后正式 reset | 无预热历史残留 |
| 进程 | 异常退出、死循环 | robotd 继续执行保护与通信 |
| 时序 | 过期、乱序、旧代次结果 | 丢弃并记录原因 |
| 资源 | 候选与当前实例内存超限 | 排队或拒绝，不挤垮控制 |
| 激活 | 反馈陈旧、仍使能、模式变化 | 拒绝切换 |

| 回滚 | 前后处理与 ONNX 都改变 | 整体恢复，状态重新初始化 |

| 行为 | 旧策略回放对照 | 在定义误差内一致 |
| 硬件 | 进程失败与通信故障 | 既有硬件保护仍有效 |

端到端性能需记录运行环境和后台负载条件。自动化测试应集中于这些有实际故障意义的边界，避免只验证示例代码逐行实现。

## 21. 待确定与待实测事项

下列事项不影响两文件总体方向，但在编码相应模块前需要落实：

1. Python＋NumPy＋ONNX Runtime 的固定版本与板端完整链路性能。
2. 实际可用数据字段、采样频率、时间戳精度和坐标定义。
3. 关节侧 MIT 目标到实际电机协议的单位和增益转换。
4. 第一版 dtype 白名单及模型输出固定形状的处理规则。
5. 控制周期范围、时限余量、预热轮数和初始化等待期限。
6. IPC 选择、最大帧大小、张量容量和内存预算。
7. 候选准备的失能要求，以及未来运动时后台准备的可行性。
8. 旧行为槽位之间的状态初始化与切换规则。
9. 单文件和总版本大小上限、历史数量、版本下载方式。
10. 固定运行环境升级后旧策略的兼容验证与保留机制。
11. 旧 `.pt/.pth` 导入入口的迁移周期。

上述技术选择可以按工程证据逐步定案；用户已经明确的两个文件、算法自由和平台硬件保护边界不应因此被重新收紧成固定 obs 或固定动作定义。
